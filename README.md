# Консольный coding agent

Учебный агент на **Kotlin/JVM 21 + MongoDB**, без агентских фреймворков.
Самодельный runtime покрывает цикл инструментов, policy, подтверждения, восстановление,
Plan Mode, бюджеты, задачи с зависимостями и журнал с откатом.

## Запуск

Нужны JDK 21, Python 3, Bash и Docker Compose (либо свой MongoDB replica set).
На Windows запускай в WSL. В IDE открой корневой `build.gradle.kts` как Gradle-проект.
Wrapper скачивает фиксированную версию Gradle; зависимости перечислены в `build.gradle.kts`.

```bash
docker compose up -d --wait
cp .env.example .env
set -a
. ./.env
set +a
./gradlew test installDist
```

`.env` не загружается приложением автоматически. Он исключён из Git.
MongoDB слушает только localhost; Compose создаёт один узел replica set для локального обучения.
Данные сохраняются в Docker volume. `docker compose down` их сохраняет.

Все дальнейшие команды запускаются из корня репозитория:

```bash
build/install/coding-agent/bin/coding-agent help
```

### Воспроизводимый пример без API-ключа

```bash
build/install/coding-agent/bin/coding-agent start \
  --task 'Исправь расчёт итоговой стоимости заказа. Тесты не меняй.' \
  --mode auto --script examples/demo.json
```

Сохрани напечатанный `run_id`. `--script` подставляет заранее записанные ответы модели;
все инструменты, проверки, Bash, MongoDB, задачи и журнал работают по-настоящему.
Это проверочный сценарий, а не имитация настоящей модели. Он содержит три зависимые задачи.
Начальный `workspace/order.py` специально содержит ошибку; `workspace/test_order.py` менять нельзя.

### Настоящая модель

Задай `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL` для доступного
OpenAI-compatible **Chat Completions** API с tool calling. Покупать ключ специально не нужно.
Затем выполни ту же команду **без `--script`**. Приложение не использует Responses API.

Для локального варианта можно использовать Ollama:

```bash
ollama pull qwen3:4b
ollama serve
```

В другом терминале загрузи `.env` из примера и запусти агента. Маленькая модель может
ошибаться в вызовах: runtime вернёт ошибку инструмента, а бюджеты ограничат число шагов.

## Управление запуском

В примерах `RUN_ID` нужно заменить реальным идентификатором.

```bash
# Отдельный режим планирования: только чтение до явного утверждения.
build/install/coding-agent/bin/coding-agent start \
  --task 'Исправь расчёт заказа, не меняя тесты' --mode safe --plan

build/install/coding-agent/bin/coding-agent status RUN_ID
build/install/coding-agent/bin/coding-agent plan RUN_ID approve
build/install/coding-agent/bin/coding-agent plan RUN_ID reject

# В safe каждое write_file и Bash отдельно ждут решения. Удаление ждёт в обоих режимах.
build/install/coding-agent/bin/coding-agent action RUN_ID approve
build/install/coding-agent/bin/coding-agent action RUN_ID deny --reason 'Не меняй этот файл'

build/install/coding-agent/bin/coding-agent resume RUN_ID
build/install/coding-agent/bin/coding-agent diff RUN_ID
build/install/coding-agent/bin/coding-agent rollback RUN_ID
```

`plan`, `action` и `recover` после решения автоматически продолжают тот же запуск.
Ожидание сохраняется в базе и завершает процесс: не нужно держать терминал открытым.
Режим `auto` сохраняет policy; он лишь убирает подтверждения записи и Bash.
Без `--plan` модель тоже строит структурированный план, но runtime сразу принимает его
в рамках разрешённого прямого исполнения. С `--plan` требуется явное решение пользователя.
Отказ от плана возвращает управление модели для нового предложения.

### Сбой во время инструмента

До выполнения сохраняются `STARTED`, снимок и расход бюджета. После — результат.
Если результат не записан, runtime не знает, было ли выполнено действие, и не повторяет его.

```bash
build/install/coding-agent/bin/coding-agent resume RUN_ID
build/install/coding-agent/bin/coding-agent recovery-diff RUN_ID
build/install/coding-agent/bin/coding-agent recover RUN_ID retry --adopt yes
# Альтернативы: fail (дать модели результат ошибки), abort (завершить запуск).
```

Если дерево изменилось, `--adopt yes|no` обязателен: пользователь решает, принадлежат ли
обнаруженные изменения этому запуску. `no` оставляет их внешними и исключает из нового
журнала изменений; ранее изменённый агентом файл с внешней правкой вызовет конфликт отката.
Пока неопределённый вызов не разрешён, rollback запрещён.

Безопасно повторяемыми считаются чтение, запись точного содержимого одного файла,
удаление одного файла (отсутствующий уже удалён), а также внутренние операции плана и задач.
Перед повтором снова применяются policy, режим и подтверждения.
**Bash не повторяется автоматически и не разрешён для явного retry**: тесты могут иметь
скрытые эффекты. Для него доступны `fail` и `abort`.

Для демонстрации настоящего падения процесса на сценарии `examples/demo.json`:

```bash
AGENT_CRASH_POINT=after_execute AGENT_CRASH_CALL=write-fix \
  build/install/coding-agent/bin/coding-agent start \
  --task 'Исправь заказ' --mode auto --script examples/demo.json
```

Процесс завершится кодом 73 после записи файла, но до сохранения результата.
Запусти `resume` без этих переменных. Другой доступный момент: `before_execute` —
после сохранения бюджета и статуса, но до побочного эффекта.

## Как устроено

| Файл | Ответственность |
|---|---|
| `src/entity/AgentRun.kt` | Состояние запуска, план, задачи, бюджет, попытки и снимки |
| `src/agent/AgentRuntime.kt` | Цикл, подтверждения, бюджет, зависимости и восстановление |
| `src/agent/Policy.kt` | Пути, команды, режимы и запреты |
| `src/agent/Tools.kt` | JSON Schema, её проверка и исполнение инструментов |
| `src/agent/Store.kt` | Транзакции MongoDB и защита от устаревших обновлений |
| `src/agent/Journal.kt` | Снимки дерева, обнаружение внешних правок, diff и откат |
| `src/agent/Model.kt` | HTTP-адаптер Chat Completions |
| `src/agent/Main.kt` | CLI и блокировка локального workspace |

Последовательность: **модель → проверка → сохранение начала → инструмент → сохранение результата → модель**.
Ответ модели может содержать несколько вызовов. Они сохраняются целой пачкой и исполняются
последовательно. Результат возвращается сообщением `role: tool` с исходным `tool_call_id`.
Повтор того же ID возвращает сохранённый результат; другой инструмент или аргументы при
старом ID дают ошибку протокола. Явный retry создаёт следующую попытку того же вызова.

Инструменты: `list_files`, `read_file`, `write_file`, `delete_file`, обязательный `Bash`,
а также `submit_plan` и `finish_task`. Bash возвращает `stdout`, `stderr`, `exitCode`.
Поля `ok` и `truncated` явно показывают ошибки и обрезанный результат.
Валидатор реализует ровно используемое подмножество JSON Schema: object/string/array,
required, additionalProperties=false, enum, minLength, minItems/maxItems.

### MongoDB

`runs` содержит один документ состояния на запуск, а `messages` — отдельный документ
на сообщение с `runId` и `sequence`. История не растит документ `runs`.
Сохранение состояния и добавление сообщений выполняются в **одной транзакции**.
Уникальный индекс `(runId, sequence)` защищает порядок; `revision` предотвращает потерю
обновления конкурентным процессом. Транзакции требуют replica set.

В callback транзакции нет Bash, HTTP или записи файлов: драйвер может повторить транзакцию.
Рабочие файлы не входят в транзакцию MongoDB; именно поэтому существуют неопределённые вызовы.
Дополнительно CLI ставит локальную файловую блокировку на workspace в `.agent-locks`
рядом с policy. Запуск рассчитан на один локальный компьютер, не на распределённых исполнителей.

Посмотреть данные, например, можно так:

```javascript
db.runs.findOne({_id: "RUN_ID"})
db.messages.find({runId: "RUN_ID"}).sort({sequence: 1})
```

### Policy и границы

Пример — `policy.json`, расположенный **вне** `workspace`. Относительные пути директорий
в policy разрешаются относительно workspace; абсолютные допустимы только внутри него.
Проверяются канонический корень, каждый компонент пути, cwd, имя инструмента и аргументы.
Неизвестное запрещено; deny приоритетнее allow. Симлинки и `..` в путях инструментов запрещены.
`protectedFiles` разрешает читать тесты, но запрещает писать и удалять их.

Команды должны совпадать с allow целиком. Поддерживаются только простые формы:
`python3 -m unittest -v` (также python, необязательные -B и -v), `pwd`, `sleep N`.
Даже добавленная в allow команда с конвейером, подстановкой, перенаправлением, произвольным
путём или `bash -c` будет отклонена. Новый вид команды требует расширить проверку.
Окружение Bash очищается от API-ключей и прочих переменных; stdout и stderr читаются
параллельно с общим лимитом, процесс имеет таймаут.

Policy **не является изоляцией ОС**: Python-тесты исполняют код с правами пользователя.
Используй учебную копию без секретов. Снимки контролируют доступную часть workspace,
но не предотвращают произвольные действия уже запущенной программы вне него.

### Бюджет, задачи и откат

Лимиты задаются через `--limits limits.example.json`. Они общие для планирования,
исполнения, resume и повторов. Если на пачку вызовов не хватает счётчиков, не исполняется
ни один вызов. Вызовы и потенциальные побочные эффекты резервируются для всей пачки;
отказанные/недопустимые действия тоже расходуют этот консервативный резерв.

Для неизвестного вывода перед действием списывается доступная квота, не больше
`maxOutputBytes`. При нормальном сохранении результата остаётся его фактический UTF-8
размер (JSON, включая служебные поля). После сбоя вся квота считается потраченной.
Меньше 1024 свободных байтов на результат не допускается; остаток передаётся инструменту,
вывод обрезается с `truncated=true`. Неудачные запросы модели тоже учитываются.

Задачи запускаются в порядке плана после успешных зависимостей; зависимости должны
ссылаться на предыдущие задачи. `finish_task` принимает ID реально исполненного вызова.
Runtime сверяет инструмент, задачу, путь, успешность и текущий хеш. Для проверки тестов
нужны Bash/unittest, exitCode=0, сообщение о ненулевом числе тестов и актуальный снимок дерева.
Одного заявления модели недостаточно. Состояние выводится чеклистом `[ ]` / `[x]`.

Перед каждой записью/удалением/Bash дерево сверяется с последним снимком. Сохраняются
содержимое и SHA-256 файлов, их создание и удаление. Из генерируемого исключается только
каталог `__pycache__`; исходники и тесты не исключены. Закрытые policy директории не читаются.
Изменение защищённого файла через Bash останавливает запуск с ошибкой.

`diff` показывает полные старую и новую версии затронутых файлов с хешами.
`rollback` предварительно проверяет policy и **все** затронутые файлы; при конфликте не
перезаписывает ни одного. Остальные файлы не трогает. Откат имеет сохранённое состояние
`ROLLING_BACK`; после сбоя повтор команды продолжает восстановление. Это явная операция
пользователя, доступная и при исчерпанном агентском бюджете. Внешние конкурентные изменения
между проверкой и записью не предотвращаются: во время запуска/отката не редактируй workspace.

Для небольшого учебного проекта снимок ограничен 512 KiB, файл — 128 KiB, число файлов — 1000,
документ состояния — 12 MiB. Лимиты файлов и снимка настраиваются в policy в безопасных пределах.
Архивы файлов хранятся в базе как Base64; отдельное объектное хранилище здесь не требуется.

## Проверки

```bash
./gradlew test
# Настоящие транзакции MongoDB, повторное открытие Store, resume и rollback:
MONGODB_TEST_URI='mongodb://localhost:27017/?replicaSet=rs0&directConnection=true' \
  ./gradlew test --rerun-tasks
```

Без `MONGODB_TEST_URI` интеграционные тесты MongoDB явно пропускаются. Остальные используют
атомарное хранилище в памяти и детерминированные ответы модели, исполняя реальные файловые
инструменты и Bash во временных каталогах. HTTP-адаптер проверяется локальным тестовым сервером.
Интеграционные тесты создают и удаляют собственные базы со случайными именами.

Проверяются: три зависимые задачи, неизменность тестов, Plan Mode, safe/auto и отказы,
повтор IDs, схемы/пути/симлинки/deny, все четыре бюджета, обрезка вывода, оба момента сбоя,
сохранение расходов после resume, доказательства задач, diff/создание/удаление/rollback
и конфликт внешней правки. HTML-отчёт: `build/reports/tests/test/index.html`.

Основные справочные источники: [tool calling](https://developers.openai.com/api/docs/guides/function-calling),
[транзакции MongoDB](https://www.mongodb.com/docs/drivers/java/sync/current/crud/transactions/),
[Kotlin/Gradle](https://kotlinlang.org/docs/gradle-configure-project.html).
